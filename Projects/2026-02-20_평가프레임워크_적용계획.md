## Part 1: 평가 프레임워크 에이전트 프롬프트 적용

### 현재 문제

```
현재 프롬프트: "시장 관점에서 분석해줘"
→ 에이전트 출력: 뜬구름 잡는 일반론

개선 프롬프트: "DVS 5개 항목을 각 1~5점으로 채점하고, TLP 단계를 판정해줘"
→ 에이전트 출력: 구체적 점수 + 근거 + 비교 가능한 데이터
```

### Step 2: AGENTS.md 프롬프트 교체

각 에이전트 spawn 프롬프트를 프레임워크 기반으로 전면 교체.

**trend-scout 프롬프트 (예시):**
```
data/idea_sessions/XXXXXXXX.json 읽고 시장 분석을 수행해줘.

반드시 vault/Research/Ideas/아이디어-평가-프레임워크.md를 먼저 읽고,
DVS/TLP/CIS 세 가지 채점표를 기준으로 분석할 것.

## DVS (수요 검증 점수) — 각 1~5점
1. dvs_trend: 네이버 검색 트렌드 (12개월 YoY 변화)
2. dvs_supply: 쿠팡 경쟁 상품 수 (포화도)
3. dvs_target: 타겟 고객 일치도
4. dvs_seasonal: 계절성 안정도
5. dvs_margin: 마진 가능성 (쿠팡가 vs 도매꾹 원가)
→ dvs_total: 합계 (/25)

## TLP (트렌드 수명주기)
- tlp_stage: 태동기|성장기|정점|하락기
- tlp_score: 1~5

## CIS (경쟁 강도) — 각 1~5점, 낮을수록 좋음
1. cis_sellers: 카테고리 판매자 수
2. cis_dominance: 상위 3 판매자 점유율
3. cis_pricefloor: 가격 바닥 근접도
4. cis_rocket: 로켓배송 점유율
→ cis_total: 합계 (/20)

## 기존 텍스트 분석
- demand: 수요 근거 (2~3문장)
- competition: 경쟁 현황 (2~3문장)
- timing: 타이밍 적절성 (1~2문장)

## 판정
- verdict: 추천|보류|반대
  - DVS ≥ 20 → 추천 경향
  - DVS < 14 → 반대 경향
  - CIS > 15 → 반대 가중
- reason: 판정 근거 (1~2문장)

결과를 JSON으로 data/idea_sessions/XXXXXXXX_trend.json에 저장.
```

### Step 4: computeVerdict 점수 기반 개선 (선택)

현재: 3인 추천/보류/반대 투표 → 다수결
개선안: 점수 가중 판정

```js
// 점수 기반 판정 (선택적 개선)
function computeVerdictV2(session) {
  const t = session.phases.trend.data;
  const tech = session.phases.tech.data;
  const biz = session.phases.biz.data;
  const cr = session.phases.critic.data;

  // Kill Criteria 체크
  if (cr?.kill_criteria?.length > 0) return '❌ 반대 (Kill Criteria 트리거)';

  // 점수 종합
  const dvs = t?.dvs_total || 0;
  const ice = tech?.ice_score || 0;
  const unit = biz?.unit_total || 0;

  if (dvs >= 20 && ice >= 7 && unit >= 20) return '🔥 강력 추천';
  if (dvs >= 14 && ice >= 5 && unit >= 14) return '✅ 추천';
  if (dvs < 10 || ice < 3 || unit < 10) return '❌ 반대';
  return '⏸️ 보류';
}
```

→ 기존 투표 기반 computeVerdict는 fallback으로 유지.

## Part 2: Phase 3 에이전트 분담 계획

### 현재 문제

Phase 3 (실행)에서 vault/Tasks/에 할일 생성하지만:
- 담당이 전부 "메인" → 누가 뭘 하는지 불명확
- 에이전트별 전문 영역이 활용 안 됨
- Day 1~7 실행 계획이 비즈니스 분석가가 만든 것이라 기술적 현실성이 떨어질 수 있음

### 7일 스프린트 에이전트 분담 템플릿

| Day | 핵심 작업 | 담당 에이전트 | 산출물 |
|-----|----------|-------------|--------|
| **Day 1** | 수요 실검증 (네이버 DataLab 쿼리, 쿠팡 실제 가격 조사) | trend-scout | data/exec_{ID}_demand.json |
| **Day 1** | 기술 설계 (MVP 아키텍처, 수정할 파일 목록) | ops-dev | data/exec_{ID}_design.json |
| **Day 2** | 비즈니스 모델 구체화 (실제 원가 기반 단위경제) | biz-writer | data/exec_{ID}_economics.json |
| **Day 2~4** | MVP 구현 (코드 작성, 스크립트 수정) | ops-dev | 실제 코드 변경 |
| **Day 3** | 중간 점검 (진행률 + 블로커) | main (에이전트) | 텔레그램 중간 리포트 |
| **Day 5** | 실제 데이터로 테스트 (소량 배치 실행) | worker (via cron) | 실행 로그 |
| **Day 6** | 결과 측정 (예상 vs 실제 비교) | biz-writer | data/exec_{ID}_result.json |
| **Day 7** | 회고 + Go/Scale/Kill 판정 | main → 사용자 | vault ADR 업데이트 |

### 에이전트별 역할 정의

**trend-scout (시장 검증)**
- Day 1 수요 실검증: 네이버 DataLab API로 실제 검색량, 쿠팡에서 상위 10개 상품 가격대 조사
- Day 6 결과 비교: 예측 DVS vs 실제 판매 데이터 비교
- 도구: trend_aggregator.py, Naver API, 쿠팡 API

**ops-dev (기술 설계 + 구현)**
- Day 1 설계: 수정할 파일, 새로 만들 파일, 예상 작업량
- Day 2~4 구현: 코드 작성, 테스트
- Day 5 배포: cron 등록 또는 스크립트 활성화
- 도구: 모든 코드 + scripts/

**biz-writer (경제성 검증)**
- Day 2 실제 원가 조사: 도매꾹 실제 가격으로 단위경제 계산
- Day 6 결과 리포트: 예상 마진 vs 실제 마진, 목표 달성률
- Day 7 회고 데이터 정리: 스코어카드 업데이트

**main (오케스트레이터)**
- Day 3 중간 점검: 각 에이전트 진행 상황 취합, 블로커 보고
- Day 7 최종 판정: Go/Scale/Kill + ADR 업데이트 + 사용자에게 보고

### Phase 3 --exec 개선안

현재 `--exec`는 단순 할일 생성만 하는데, 개선 시:

1. `--exec ID` → 할일 생성 + Day별 에이전트 배정 포함
2. Day 1 자동 시작: trend-scout에게 수요 검증 지시
3. Day 3 중간 리포트 크론 또는 알림
4. Day 7 회고 알림 + 스코어카드 비교표

### 구현 우선순위

```
Step A (프롬프트만, 코드 안 건드림):
1. AGENTS.md 에이전트 프롬프트를 프레임워크 기반으로 교체
2. 프레임워크 문서를 에이전트가 참조하도록 프롬프트에 경로 추가
→ 이것만으로도 토론 품질 대폭 향상

Step B (PHASE_SCHEMA 확장):
3. run_idea_discussion.js PHASE_SCHEMA에 점수 필드 추가
4. buildTelegramCard / buildVaultMarkdown에 점수 표시
5. computeVerdict에 점수 기반 판정 추가 (fallback 유지)

Step C (Phase 3 실행 자동화):
6. --exec에 에이전트 분담 포함하여 할일 생성
7. Day 3 중간 점검 알림 구현 (크론 or process_idea.js --checkpoint)
8. Day 7 회고 + 스코어카드 비교 구현
```

## Day 7 Go/No-Go 스코어카드

| 기준 | 목표 | 실제 | 통과? |
|------|------|------|-------|
| DVS 실검증 (Day 1 vs 예측) | ±20% 이내 | | |
| 단위 이익률 | ≥ 30% | | |
| 등록 성공률 | ≥ 70% | | |
| 구현 소요 시간 | ≤ 2일 | | |
| Kill Criteria 트리거 | 0건 | | |

- 4/5 통과: **Scale** (프로덕션 크론으로)
- 3/5 통과: **Iterate** (1스프린트 더)
- 2/5 이하: **Kill** (아카이브 후 다음으로)
