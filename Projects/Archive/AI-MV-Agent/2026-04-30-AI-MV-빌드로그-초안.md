## 빌드로그 아웃라인

### Problem

뮤직비디오 편집에서 가장 먼저 돈이 되는 병목은 “AI가 완성본을 만들어주는가”보다 “수십~수백 개 촬영본 중 지금 타임라인에 올릴 컷을 얼마나 빨리 찾는가”다. 개발자/기술 편집자에게는 로컬 프로젝트를 유지하면서도 자연어로 컷을 찾고, 선택한 클립을 FCPXML로 넘기는 작고 검증 가능한 assistant가 더 설득력 있다.

### What changed

Repo가 초기 공개 준비 상태로 정리되면서, MV BRAIN을 하나의 개발자 제품으로 설명할 재료가 갖춰졌다. README는 CLI pipeline과 local web UI를 같은 제품 스토리로 묶고, `mv-brain demo`로 실제 영상·Qdrant 서버·provider API key 없이도 clip browser/output 흐름을 보여줄 수 있다고 설명한다. 오늘 빌드로그의 각도는 “public-ready release 이후, 데모 가능한 문제 정의를 고정하는 단계”다.

### Technical detail

기술적으로 강조할 부분은 세 가지다.

1. `visual`, `audio`, `style` 3-channel embedding 구조로 “보이는 것 / 음악 에너지 / 편집상 쓸만함”을 분리한다.
2. `clip_archive`, `mv_refs`, `brain_refs` 컬렉션 모델로 원본 촬영본, 레퍼런스 MV, 편집자 취향 기억을 구분한다.
3. `mv_brain/output/`과 `tools/fcpxml-mcp-server`가 FCPXML handoff를 제품의 끝점으로 만든다. 즉, 데모는 채팅 UI에서 끝나는 게 아니라 실제 편집 타임라인 파일로 끝나야 한다.

### Demo angle

90초 개발자 데모는 아래 흐름이면 충분하다.

1. `mv-brain demo`로 샘플 클립 메타데이터와 `output/demo_roughcut.fcpxml`을 준비한다.
2. UI 또는 CLI에서 “에너지 높은 후렴용 댄스 씬” 같은 자연어 질의를 보여준다.
3. 후보 클립 선택 → FX 추천 → FCPXML 출력 → Final Cut Pro로 넘길 수 있는 파일이 생겼다는 점을 보여준다.

### Next experiment

다음 실험은 “no-media demo가 진짜 포트폴리오 캡처로 보이는가”를 확인하는 것이다. 실제 provider/API 없이 `mv-brain demo` 결과물만으로 README 하단에 3~5컷짜리 데모 스토리보드와 터미널 명령/출력 예시를 붙인다. 목표는 GitHub 방문자가 60초 안에 “이건 자동 MV 생성기가 아니라, FCPXML까지 이어지는 local-first clip triage assistant”라고 이해하게 만드는 것이다.
