# ADR-030: 에러 학습 루프 설계

> 에이전트가 같은 에러를 반복하지 않도록 패턴을 기록하고 학습하는 시스템

---

## 1. 문제 정의

### 현재 상태
- self_healing_monitor → 인시던트 감지 → 플레이북 실행 → 반복
- **같은 에러가 계속 발생해도 대응이 동일** (학습 없음)
- 837건 자가치유 이력 중 303건이 `playbook-high-risk-queued` (해결 안 됨)
- patch_queue에 103건 중 80건이 `TIMEOUT_RELAY` (같은 카테고리 반복)

### 핵심 약점 6가지 (이전 조사 결과)
1. **반복 패턴 학습 부재**: 같은 카테고리 에러가 N번 반복돼도 대응 변화 없음
2. **근본원인 추적 단절**: 인시던트 → 플레이북까지만. "왜 이것이 반복되는가" 기록 없음
3. **액션 효과 측정 없음**: `disable_job_temporarily` 후 에러가 줄었는지 모름
4. **고위험 큐 정체**: patch_queue 103건 중 101건이 수동 cleanup
5. **에이전트 피드백 루프 없음**: 에이전트가 과거 에러를 참조하지 않음
6. **Vault 구조화 부족**: Runbook 3개뿐, 에러 패턴 지식이 코드에만 존재

---

## 2. 설계 원칙

### 데이터 분리 (CRITICAL)
```
에러 데이터 (runtime, 자주 변경)  → data/ (서버 로컬, Syncthing X)
에러 지식 (패턴, 드물게 변경)     → vault/ (Syncthing O, 사람 읽기용)
에러 검색 (벡터 인덱스)           → rag-data/ ChromaDB (로컬)
```

이유:
- vault는 Syncthing sendreceive로 Mac과 양방향 동기화
- 에러 로그를 vault에 넣으면 → 수초마다 파일 변경 → 동기화 부하 + 충돌 위험
- 사용자가 vault 직접 편집 안 해도 Syncthing conflict file 생성 가능
- `data/`는 서버 로컬 → 충돌 0, 성능 제한 없음

### 벡터 검색 (ChromaDB 유지)
- Pinecone 불필요: 290 청크 / 11MB → ChromaDB HNSW로 충분
- 비용 0 vs $70+/월, 네트워크 레이턴시 없음
- 개선: 한국어 임베딩 모델 교체 (향후)

### 5-1. 패턴 추출 로직

```javascript
// 입력: incidents.ndjson + self_healing_incidents.json
// 출력: error_patterns.json

// 패턴 = 동일 (category + root_symptom 유사도 80%+) 그룹
// 유사도는 문자열 Jaccard similarity (벡터 불필요 — 에러 메시지는 구조적)

패턴 스키마:
{
  pattern_id: "pat_a1b2c3d4",
  category: "TIMEOUT_RELAY",
  root_symptom_template: "lane duration {N}ms exceeds delay threshold {N}ms",
  first_seen: "2026-02-23T...",
  last_seen: "2026-03-01T...",
  occurrence_count: 80,

  // 효과 추적
  actions_tried: [
    {
      action: "disable_job_temporarily",
      times_applied: 15,
      times_resolved: 3,     // 24h 내 재발 안 함
      effectiveness: 0.20,   // 20% — 비효과적
      last_applied: "..."
    },
    {
      action: "increase_recovery_backoff",
      times_applied: 12,
      times_resolved: 8,
      effectiveness: 0.67,   // 67% — 효과적
      last_applied: "..."
    }
  ],

  // 에스컬레이션
  escalation_level: "root_cause_needed",  // 3회+ 반복
  suggested_root_fix: "gateway_channel_separation",

  // 관련 Runbook
  linked_runbook: "vault/Runbooks/자동생성-TIMEOUT_RELAY.md"
}
```

### 5-2. 효과 추적 로직

```
매 실행 시:
1. 지난 24시간 내 실행된 액션 수집 (self_healing_incidents.json)
2. 각 액션 후 같은 패턴의 에러가 24시간 내 재발했는지 확인
3. action_effectiveness.json 업데이트:
   - 재발 없음 → resolved +1
   - 재발 있음 → ineffective +1
4. 효과율 < 30%인 액션 → 플레이북에서 비활성화 권고
5. 효과율 > 70%인 액션 → 해당 패턴의 1순위 대응으로 승격
```

### 5-3. 에스컬레이션 판단

| 조건 | 레벨 | 액션 |
|------|------|------|
| 같은 패턴 3회 이내 | `monitoring` | 기존 대로 자동 대응 |
| 같은 패턴 3~10회 | `pattern_detected` | 텔레그램 알림 + 효과 분석 시작 |
| 같은 패턴 10회+ | `root_cause_needed` | HITL 요청: 근본 수정 필요 |
| 효과율 0% 액션 | `action_deprecated` | 해당 액션 자동 적용 중단 |

### 5-4. Runbook 자동 생성 (월 1회)

```markdown
---
type: runbook
note_status: permanent
confidence_level: medium
source_agent: error-pattern-learner
generated_via: cron
created: 2026-03-01
reviewed_at: 2026-03-01
---

# TIMEOUT_RELAY 에러 대응 Runbook

## 패턴 요약
- 발생 횟수: 80회 (2026-02-23 ~ 현재)
- 근본 증상: lane duration exceeds delay threshold
- 추정 원인: gateway 채널 분리 필요

## 효과적 대응 (효과율 순)
1. increase_recovery_backoff (67%)
2. strengthen_alerting (45%)
3. ~~disable_job_temporarily (20%)~~ — 비효과적

## 근본 수정 필요
- gateway_channel_separation (patch_queue에 80건 대기)

## 관련 인시던트
- inc_574aa835..., inc_d734ee37..., ...
```

이렇게 하면:
- **에러 데이터**: `data/` (JSON, 충돌 0)
- **에러 지식**: `vault/Runbooks/` (월 1회, Syncthing 안전)
- **에이전트 참조**: `vault-search`로 Runbook 검색 가능

## 9. 구현 순서

### Phase 1: 패턴 추출 (1일)
- `error_pattern_learner.js` 작성
- `error_patterns.json` 스키마 정의
- 기존 incidents.ndjson + self_healing_incidents.json 파싱

### Phase 2: 효과 추적 (1일)
- `action_effectiveness.json` 스키마
- 24시간 재발 감지 로직
- 효과율 계산

### Phase 3: 에이전트 연동 (0.5일)
- `self_healing_monitor.js` 수정: 패턴 DB 조회 우선
- SOUL.md 에러 대응 섹션 추가

### Phase 4: Runbook 자동 생성 (0.5일)
- `--generate-runbooks` 모드 구현
- vault/Runbooks/ 자동 생성
- 크론잡 등록

### Phase 5: 모니터링 (0.5일)
- `--status` 모드 (패턴 현황, 효과율 순위)
- 텔레그램 주간 리포트 (에러 패턴 트렌드)
- 크론잡 등록
