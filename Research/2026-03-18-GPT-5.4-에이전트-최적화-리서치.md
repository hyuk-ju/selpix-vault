# GPT-5.4 에이전트 최적화 리서치

## 1. GPT-5.4 vs GPT-5.3 Codex 주요 차이

| 항목 | GPT-5.3 Codex | GPT-5.4 |
|------|---------------|---------|
| 컨텍스트 윈도우 | 400K | 1,050,000 (1.05M) |
| 출력 상한 | - | 128K tokens |
| SWE-Bench | ~80% | ~80% (코딩 동등) |
| Computer Use | 64% | 75% (인간 기준 72.4% 초과) |
| GDPval (지식 작업) | 미설계 | 83% |
| 토큰 효율성 | 기준 | 47% 절감 (동일 정확도) |
| 특화 방향 | 터미널 중심 코딩 | 범용 에이전트 (코딩+도구+지식) |

**핵심**: GPT-5.4는 GPT-5.3 Codex의 코딩 능력을 흡수하면서 도구 사용, 지식 작업, 컴퓨터 사용을 대폭 개선. 터미널 중심 속도 민감 작업만 5.3 Codex가 우위.

## 2. 에이전트 도구 호출 최적화

### 2.1 tool_choice 파라미터

```json
{
  "tool_choice": {
    "allowed_tools": ["search", "code_interpreter"],
    "mode": "auto"
  }
}
```

- `allowed_tools`: 전체 tools 배열에서 실제 사용 가능한 도구를 서브셋으로 제한
- `mode`: `auto` (모델 판단) 또는 `required` (반드시 하나 호출)
- `"none"`: 도구 없이 응답 강제

### 2.2 parallel_tool_calls

- 기본값 `true` — 모델이 한 턴에 여러 도구 동시 호출 가능
- `parallel_tool_calls: false` — 정확히 0개 또는 1개만 호출
- 순서 의존성 있는 도구 체인에서는 `false` 권장

### 2.3 Tool Search (GPT-5.4 신기능)

가장 큰 혁신. 도구 정의를 지연 로딩하여 토큰 47% 절감:

1. 모델에 도구의 **경량 목록**(이름+설명만)과 `tool_search` 기능 전달
2. 모델이 특정 도구 필요 시 **그때** 전체 스키마를 검색/로드
3. 대규모 MCP 서버 환경에서 특히 유효

**OpenClaw 적용 가능성**: 현재 도구 5개로 필요성 낮음. MCP 15개+ 시 재검토 (MEMORY.md 기록과 일치).

## 3. 토큰 최적화 전략

### 3.1 272K 임계점 (CRITICAL)

- **272K 초과 시**: 전체 세션 Input 2x ($5.00/1M), Output 1.5x ($22.50/1M)
- **임계점은 전체 적용**: 초과분만이 아닌 전체 대화에 높은 요금 적용
- 250K input + 20K output = ~$0.925 vs 300K input + 20K output = ~$1.95 (2.1x 차이)

| 범위 | 정확도 | 비용 효율 |
|------|--------|-----------|
| 0-127K | ~97% | 표준 |
| 127K-272K | ~97% | **최적 구간** |
| 272K+ | 유지 | 2x 비용 점프 |

### 3.2 캐싱 활용

- Cached input: $0.25/1M (표준의 1/10)
- `previous_response_id` 사용 시 캐시 히트율 상승 + 재추론 방지
- Responses API 사용이 Chat Completions보다 캐싱에 유리

### 3.3 추론 토큰 제어

- `reasoning_effort` 파라미터로 단순 작업 시 추론량 축소
- 과도한 reasoning → 응답 지연 + 토큰 낭비의 주 원인

## 4. 시스템 프롬프트 Best Practices

### 4.1 구조화된 프롬프트 (RACE 프레임워크)

- **R**ole: 역할 정의
- **A**ction: 수행할 작업
- **C**ontext: 배경 정보
- **E**xpectation: 기대 출력 형식

### 4.2 XML 태그 활용

```xml
<instruction_spec>
  <role>...</role>
  <tools_policy>...</tools_policy>
  <output_contract>...</output_contract>
  <completion_criteria>...</completion_criteria>
</instruction_spec>
```

GPT-5.4는 XML 구조화 프롬프트에서 instruction adherence가 크게 향상됨.

### 4.3 출력 계약 (Output Contract)

- 반환할 섹션, 순서, 형식을 명시적으로 정의
- JSON/SQL 등 파싱 민감 형식: "해당 형식만 출력하고 산문 추가 금지" 명시
- 길이 제한은 특정 섹션에만 적용되도록 지정

### 4.4 완료 조건 명시

- "정의 of done"이 없으면 모델이 끝없이 탐색/계획하는 overthinking 발생
- 명시적 중단 조건 + 단일 self-check를 프롬프트에 포함

## 5. 알려진 문제/주의사항

### 5.1 과도한 순종 (Over-deference)

에이전트 환경에서 모델이 너무 조심스럽게 행동하는 경향. 시스템 프롬프트에 persistence 지시를 추가하면 완화.

### 5.2 Overthinking

사소한 질문에도 광범위한 추론을 수행. 원인:
- `reasoning_effort`가 과도하게 높음
- 프롬프트에 완료 기준이 없음
- 상충하는 지침이 존재

### 5.3 장황함 (Verbosity)

- Responses API의 `verbosity` 파라미터 활용
- 출력 계약으로 추가 통제

### 5.4 Instruction 실행 방식 변경

- GPT-5.3 Codex: 실행 중 새 지시 주입 가능
- GPT-5.4: 실행 전 reasoning plan 제시 → 수정 후 실행 (proactive correction 패턴)

## 6. OpenClaw 적용 권장사항

1. **모델 분리 전략 유지**: 분석/추론 → 5.4, 단순 스크립트 → spark (MEMORY.md 기존 전략과 일치)
2. **272K 임계점 모니터링**: 세션 토큰 추적하여 임계 초과 방지
3. **Tool Search 도입 시기**: MCP 도구 15개 이상 시 도입 검토
4. **시스템 프롬프트 구조화**: SOUL.md에 XML 태그 기반 구조 적용 고려
5. **reasoning_effort 분기**: 작업 복잡도에 따라 동적 조절
6. **previous_response_id 활용**: 멀티턴 에이전트 루프에서 캐시 히트율 극대화
