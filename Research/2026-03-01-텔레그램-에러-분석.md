# 텔레그램 에러/알림 과다 분석

## 요약

텔레그램에 "중요 에러"가 많이 뜨는 이유는 **실제 시스템 장애가 아닌 알림 설정 문제**가 핵심. 3가지 주요 원인이 전체 노이즈의 90%를 차지.

## 2. 원인별 상세 분석

### 원인 A: team-dispatch + ops-directive-handler의 잘못된 alert level (전체 노이즈 95%)

**현상**: 15~20분마다 "0건 처리", "대기 없음"이 `warning` 레벨로 기록

**근본 원인**: `alert_config.json`에서 두 잡의 level이 `warning`으로 설정됨

```json
"team-dispatch": { "level": "warning", "note": "팀 디스패칭" }
"ops-directive-handler": { "level": "warning", "note": "운영 지시 처리" }
```

**문제점**: "할 일 없음"은 정상 상태. 이것이 warning으로 분류되면:
- daily_digest에 매일 ~192건의 경고가 쌓임
- 사용자가 다이제스트를 열면 대부분이 무의미한 "0건" 보고
- 진짜 경고가 묻혀서 보이지 않음

**수정 방안**: 두 잡의 level을 `info`로 변경. 단, 실제 처리건이 있을 때만 `warning`으로 에스컬레이션하는 게 이상적.

```json
"team-dispatch": { "level": "info", "note": "팀 디스패칭 — 사일런트, 알림 발생 시만 warning" }
"ops-directive-handler": { "level": "info", "note": "운영 지시 처리 — 사일런트, 처리 건 있을 때만 warning" }
```

---

### 원인 B: pipeline_health_check "연속 에러" 반복 발화 (매 6시간 CRITICAL)

**현상**: health_check.log에 반복적으로 나타남:
```
🚨 파이프라인 건강 알림
• 연속 에러: 최근 5건 중 4~5건 실패
```

**근본 원인**: `register_log.json`의 최근 20건 중 19건이 동일한 에러:
```
FAIL | 구매옵션/단위 메타 검증 실패: 수량=1, 색상=블랙
FAIL | 구매옵션/단위 메타 검증 실패: 수량=1, 색상=혼합색상
...
```

이 에러는 **쿠팡 등록 API의 옵션 메타데이터 검증 로직** 문제. 새 상품이 등록될 때마다 같은 검증 실패가 반복되고, `pipeline_health_check.js`가 매 6시간마다 마지막 5건을 체크해서 3건+ FAIL이면 CRITICAL 알림을 전송.

**문제점**:
1. **같은 에러를 반복 알림**: 한번 인지한 문제를 6시간마다 다시 알림
2. **실제 심각도 불일치**: 메타 검증 실패는 시스템 장애가 아닌 데이터 품질 이슈
3. **알림 피로**: 같은 메시지가 반복되면 진짜 CRITICAL도 무시하게 됨

**수정 방안** (2가지):
1. **즉시**: register_log.json의 스테일 FAIL 데이터를 정리하거나, `pipeline_health_check.js`에 "동일 에러 반복 시 1회만 알림" 로직 (dedup)
2. **근본**: `cron_register_product.js`의 옵션 메타 검증 로직 수정 → 구매옵션 형식을 올바르게 생성하도록

---

### 원인 C: 품절 모니터링 critical 레벨 과민 반응

**현상**: "품절 모니터링: 감지 49건, 판매중지 0건" 이 `critical`로 기록

**문제점**: 감지만 하고 판매중지 0건이면 실질적 액션이 없음. 대량 감지(49건)가 매번 critical로 뜨면 노이즈.

**수정 방안**:
- 판매중지 실행 건이 있을 때만 critical
- 감지만 한 경우 → warning (다이제스트)
- 또는 threshold 도입: 감지 10건 미만 → info, 10건+ → warning, 판매중지 실행 시 → critical

---

### 원인 D: Gateway TIMEOUT_RELAY (부수적)

**현상**: `incidents.ndjson`에 `TIMEOUT_RELAY` 인시던트 반복
```
lane duration 147896ms exceeds delay threshold 120000ms
```

**근본 원인**: 크론 잡 실행이 타임아웃(120초) 초과. 2/27에 집중 발생.

**관계**: 에러 자체라기보다 에러 결과로 발생하는 연쇄 효과. 메시지 큐가 밀리면서 처리 지연.

**수정 방안**: 타임아웃 증가 또는 무거운 잡의 분리 실행

---

### 원인 E: ralph-loop-autopilot의 critical 분류 (부수적)

**현상**: ralph 루프가 정상 작업(코드 수정, 빌드)을 수행하는데 `critical`로 기록 (8건)

**문제점**: `alert_config.json`에는 ralph이 `info`로 설정되어 있는데, gateway의 크론 결과 리포트에서 critical로 분류됨. 이는 gateway가 크론 잡의 에러/성공을 판단할 때 다른 기준을 적용하는 것으로 보임.

**확인 필요**: gateway의 크론 결과 → alert level 매핑 로직

## 3. 우선순위 수정 계획

### P0 — 즉시 (노이즈 95% 제거)

| 대상 | 변경 | 파일 |
|------|------|------|
| team-dispatch | level: warning → info | alert_config.json |
| ops-directive-handler | level: warning → info | alert_config.json |

**효과**: 경고 339건 → 17건으로 감소 (95% 노이즈 제거)

### P1 — 단기 (반복 CRITICAL 제거)

| 대상 | 변경 | 파일 |
|------|------|------|
| pipeline_health_check | 동일 에러 dedup + 쿨다운 (24h) | pipeline_health_check.js |
| register_log 정리 | 스테일 FAIL 항목 정리 또는 로그 rotation | 운영 작업 |
| 옵션 메타 검증 | 구매옵션 형식 수정 | cron_register_product.js |

**효과**: 매 6시간 반복 CRITICAL → 1일 1회 또는 상태 변화 시만

### P2 — 중기 (정밀 튜닝)

| 대상 | 변경 | 파일 |
|------|------|------|
| 도매꾹 품절 모니터링 | 감지만 시 warning, 판매중지 시만 critical | alert_config.json 또는 크론 프롬프트 |
| ralph-loop-autopilot | gateway 크론 결과 level 매핑 확인 | gateway 설정 |
| team-dispatch 조건부 escalation | 실제 알림 발송 시만 warning으로 승격 | team_dispatcher.js |
